# Permanent monthly publication and exact request evidence

Schema 25 adds an internal publication writer and an optional archived branch in the permanent request resolver. It does not activate a public route, schedule archival, delete source rows, or establish current historical visit authority.

A publication starts only from a completed supported monthly v2 semantic run. The writer checks the closed runner cursor, frozen session identity, manifest header and current history generation. A verified session without that completed run is insufficient. Original proof provenance is retained independently of disposable staging tables.

Each advance authenticates the pinned encrypted manifest and one bounded part. It indexes at most eight records and 256 KiB of record plaintext. Each locator retains the exact table/key, part ordinal, descriptor hash, original record hash and record byte count. Before inserting an event or correction locator, the same native transaction compares every immutable source field and the existing permanent request owner, center, fingerprint and declared encoding. It retains the sealed receipt. Audit aliases compare against the original audit projection. Linked records belong to the visit's original-arrival month; unmatched observations belong to their observed month. Captured mutable profiles, visits and reviews remain snapshot evidence.

An advance claims a database-clock lease and revision. Every candidate mutation checks that exact lease/revision, current proof and generation, and the backup maintenance barrier. Part and build counters advance atomically. A final native SQL assertion rolls back the page if its checkpoint guard matches no row. A lost reply is recovered through the stored revision. Pending candidates are invisible to readers.

The terminal native transaction marks the build published, inserts the immutable descriptor, and creates ready availability. It checks exact EOF and totals. Part reconciliation reads at most 256 candidates; full locator totals are checked only at terminal commit, under the 20,000-record ceiling. The first supported base is unique per center/month. There is no current-visit or later-addendum authority implied by this constraint.

Locator version 1 starts with a 64-character zero digest. For each page it hashes UTF-8 `JSON.stringify({ prior, locators })`; locator properties in order are `table`, `key`, `part`, `offset`, `descriptorSha256`, `recordSha256`, `recordBytes`. Page ordering follows manifest part order and original record order, with the eight-record/256 KiB limit. The final descriptor records that digest and exact counts. Schema 26 catalog reconciliation reconstructs this exact chain before restoring availability. See [reconciliation](archive-publication-reconciliation.md).

The optional request resolver obtains the permanent key, retained live evidence, history state and published locator in its initial database snapshot. Ownership and changed-payload checks precede object access. Consistent live evidence is preferred. Otherwise it authenticates the exact manifest and part, then rechecks the permanent key, live authority, generation, availability and selected locator before returning the original response. Missing or inconsistent evidence returns unavailable; it never grants insertion permission. Authenticated event GET and event/correction POST replay routes now supply the read-only archive dependency when archive storage is configured. Historical visit, range and report routes still require separate current-authority and completeness support.

The backup snapshot includes all six publication tables and pins both completed legacy archive roots and every committed publication root, including unavailable publications. Exact duplicates collapse; conflicting archive identities fail the snapshot. The current 52-table inventory uses scalar count subqueries in one statement, keeping the lock/count/schema/reference snapshot within four native statements. Restoration preserves original publication provenance and locators while marking availability unavailable and invalidating unfinished work.

Local tests cover exact compact/object/null receipts, staging cleanup independence, ownership and integrity failures, changes during object reads, source reconciliation, native rollback, lost replies, backup pinning, repeated restore resets and independent encrypted SQL-plus-v2 recovery after the source runtime is closed. These establish retained evidence, not readiness of a restored catalog for operational lookup.

Restored-generation catalog reconciliation and bounded cleanup of invalid unpublished candidates are implemented internally. [Cleanup](archive-publication-abandonment.md) releases temporary claims while retaining the failed build, permanent ownership and committed evidence. Authenticated archived event receipt GET is now integrated locally. Archived POST replay is also integrated locally; see [its checkpoint](archive-post-replay-checkpoint-2026-09-16.md). Interval/report/correction authority, addenda, holds, source eviction, deployed measurements and live recovery/cutover acceptance remain unfinished. See [the receipt lookup checkpoint](archive-public-reader-checkpoint-2026-09-16.md). Live source records stay in D1. Local tests do not establish Free-plan capacity.

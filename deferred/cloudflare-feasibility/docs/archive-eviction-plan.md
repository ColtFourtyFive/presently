# Historical eviction, replay, and correction plan

September 16 update: migration 0017 provides permanent request ownership and shadow intervals. Migration 0018 provides private authenticated semantic staging. The [311-test checkpoint](archive-staging-checkpoint-2026-09-16.md) also validates live-source retry resolution. Exact R2 replay, bounded semantic verification, publication, historical authority, reporting integration and safe deletion remain unfinished. Archive locations and source visit deletion remain disabled.

Prepared September 15, 2026 from the current local implementation. **Design and implementation plan only: no deletion path, migration, deployment, or retention expiry is enabled by this document.**

Move bulky, closed attendance evidence from D1 to verified private R2 while preserving at least two years of reviewable history, permanent accepted-request identity, current overlap protection, and independently recoverable records. Keep current profiles, pickup authority, open visits, unresolved reviews, and held records operational in D1. The first release should have no automatic R2 history deletion.

## Required invariants

1. **Preservation, not expiry.** Ninety days is the minimum age for considering D1 detail removal, not the retention period. Retain original observations, original/effective visit times, every correction, review resolution, audit provenance, frozen accepted receipts, and the captured identity context for at least two years. Active holds override storage-age rules. The initial policy keeps historical objects indefinitely; introducing expiry is separate work.
2. **Permanent accepted IDs.** An accepted event or correction ID remains reserved for the installation's lifetime, including after center transfer and recovery. The same payload resolves to the original accepted event/correction and receipt, without applying attendance again. A changed payload is rejected even if its date is recent, its student differs, or R2 is unavailable. Authentication and center scoping still precede disclosure.
3. **Authoritative intervals.** Each visit has one current effective interval and version across live and historical storage. All new arrivals, departures and corrections check the union atomically. Half-open interval overlap remains `other.start < proposed.end AND other.end > proposed.start`, with an open end treated as infinity; preserve the existing stricter arrival rule where applicable. Tests must settle zero-duration and touching-boundary behavior without silently changing current semantics.
4. **Immutable evidence, versioned projection.** Accepted observations and corrections never change. The current visit/review projection can advance only through an explicit, ordered operation. An R2 base object is never overwritten. A later correction cannot rewrite the receipt returned for an earlier attendance event.
5. **No unexplained absence.** Missing, corrupt, unsupported, incomplete, or inconsistent evidence returns a specific unavailable error. It cannot become an empty result, a new attendance insertion, a partial successful report, or an eviction approval.
6. **Transactional publication.** Switching a record from live detail to historical detail, reserving its IDs, retaining its effective interval, changing report epochs, recording removal, and deleting the approved source closure happen in one D1 transaction. R2 must already contain and have passed independent readback of the complete evidence.
7. **Stable ownership.** Student/staff/guardian/device references are bound to the captured center. A same-ID row currently in another center or an altered profile is never used to repair missing historical context.

## Persistent data to add

Use new additive migrations with the next available numbers; other CRM migrations are being developed concurrently. Do not reserve `0013` or alter migration 0008 in place. Table names below are proposed contracts, not existing schema.

### Immutable publication and evidence location

Extend archive jobs/catalog with `kind`, `base_archive_id`, publication generation/sequence, semantic format version, and explicit states distinguishing an uploaded copy, a semantically verified publication, and an eviction source. Retain the old `complete` meaning for v1 copies; never reinterpret old copies as eviction-ready. Keep monthly uniqueness for base publications while allowing addenda for that base.

Add `history_publications` with an immutable publication ID, center, original month/timezone, base ID, sequence, prior publication digest, exact manifest key/hash, schema/semantic version, counts, coverage, and verification metadata. A small `history_month_heads` row selects the published revision with compare-and-swap. The head is a projection; all previous publication entries remain. Failed/staged R2 objects have no visible head.

Build exact locators containing publication ID, table, record key, part number, row hash and immutable manifest hash. Initially retain/reuse `archive_members` and `archive_parts` as evidence-location backing. Do not remove their hashes to save space before an authenticated replacement index and recovery test exist. Distinguish multiple captured versions of mutable identity/visit context from a single immutable observation/correction identity.

### Permanent identity and retry registry

Add `history_request_keys` with global request ID, owning center, kind (`attendance_event`, `attendance_correction`, or reserved standalone-audit identity), original payload hash and hash/canonicalization version where applicable, student/visit reference, and immutable evidence locator. Match the current event/correction/audit cross-type collision domain; do not weaken it by making `(center_id, id)` the only uniqueness constraint. A derived audit is an alias of its event/correction owner, not a second conflicting registration. Visit and relationship keys remain in their own typed namespaces.

The registry stores the exact existing `payload_hash` representation. Current production writes use 44-character base64 SHA-256; supported legacy hex is preserved and compared using its declared algorithm. Do not recompute old hashes with a different JSON property order, date normalization, or field set. Store no names, reason text, credentials, or full duplicate receipts in this minimal registry.

Before removal, the locator must resolve the complete immutable source row, including the sealed `result_visit` string and all decoder inputs (`visit_id`, `student_id`, `action`, `observed_at`). Preserve legacy object receipts, tuple-v2 receipts, and the sealed text `"null"` for unmatched exceptional departure. SQL NULL is unsealed and ineligible. Immutable corrections retain their entire `correctionView` evidence and payload hash.

A permanent hash alone rejects changed payloads but cannot return an exact accepted receipt. Therefore its referenced evidence, encryption keys, and lookup metadata must also remain recoverable indefinitely under the initial permanent-retry contract. A future two-year deletion policy would need to retain a complete equivalent receipt elsewhere or explicitly change that contract; silently expiring the R2 receipt is not compatible.

Use the registry in both API lookup and database insertion guards. The early API read alone has a race with eviction or a concurrent acceptance. A losing insert must reload the owning key and compare the payload, never turn the conflict into an unscoped record disclosure. All event-status, event retry, correction retry, and audit ID allocation paths need the same behavior. Keep retries out of business-state updates and avoid duplicate audit effects.

### Current historical visit and review projection

Add `history_visit_heads` keyed by visit ID with center/student, original arrival month, original times, current effective start/end, current version, review state, current evidence/publication reference, and residency (`live` or `archived`). Keep names and full provenance in verified evidence. Index `(center_id, student_id, effective_start, visit_id)` for overlap checks and `(center_id, effective_start, visit_id)` for date lookup. Maintain one authority for the effective projection; do not independently update both a historical head and a live visit without transactional equality checks.

Add a compact review/unmatched-event lookup where needed to find resolved evidence by original observation time, event ID and student. Unmatched exceptional departures have no visit interval; they still require permanent retry and review/audit closure. Retain minimal ownership records for referenced devices after revocation without retaining tokens or sessions.

The initial backfill can populate the projection for all visits, then use transactional triggers for subsequent live changes. Shadow-compare it to live records before using it as the sole overlap authority. This costs D1 space: measure it with realistic UUIDs, 44-character hashes, corrections, holds, and all CRM tables. Do not claim the earlier 35 MB detailed-data experiment is the final footprint.

### Holds and durable work records

Rebuild `archive_holds` in a forward migration so a visit hold can reference a durable historical visit identity instead of requiring the deletable `visits` row. Preserve every existing hold, release, reason and actor. Student/visit scope must be validated by D1 triggers in the transaction that inserts the hold; the current API pre-read is insufficient after removal becomes possible. Preserve released holds as evidence; never delete them to satisfy a foreign key.

Add bounded `history_eviction_jobs` and `history_eviction_items` recording requested scope, verified publication digests, exact selected closure, source versions/hashes, lease/fence, state, last verification time, and committed deletion counts. An immutable eviction receipt identifies each completed batch. Add an append-only `history_changes` outbox for late corrections, review transitions and newly eligible records awaiting addendum publication. The outbox is authoritative D1 evidence until the corresponding immutable R2 publication is verified and committed.

Every new authoritative table must participate in backup write barriers, `BACKUP_TABLES`/count reconciliation, migration tests and recovery. Any staging exception must be explicitly marked non-authoritative and reset on recovery. No global boolean may disable immutable deletion guards.

## Full dependency and semantic verifier

Implement a shared verifier used by publication, the post-eviction reader, the eviction preflight, backup/update verification and independent recovery. Keep the current cryptographic/size checks and add relationship semantics. Process bounded pages into private staging/indexes; do not load two years of records into Worker memory.

| Evidence | Required independent checks |
| --- | --- |
| Visit | Captured center/student exist; original arrival and accepted arrival agree; departure observation/original departure agree where present; staff and guardian references resolve; effective version is reconstructed from the accepted base and ordered corrections; open/pending state prevents removal. |
| Observation | Required enums, times, actor/channel/device ownership, payload-hash algorithm, full sealed receipt shape, and referenced student/visit agree. Recompute the accepted request fingerprint using its versioned canonicalization. Unmatched exceptional departures remain explicitly unmatched. A receipt is the state at acceptance, not the latest visit projection. |
| Correction | Same-center visit and actor; unique permanent correction ID; `expected_version` and prior times match the immediately preceding visit projection; new interval is valid; next version is exactly defined. Preserve recorded time separately from effective time. Never order solely by timestamp when two writes share a millisecond. |
| Review | Its event, optional visit and student agree; reason/status/resolution/actor/times are coherent; a current pending review blocks removal. Historical review changes are appended and ordered rather than replacing the old resolution. |
| Audit | Preserve the exact logical `audit_timeline` result, including source-derived rows and physical divergent/custom rows. Validate entity references by type. Generated attendance/correction audit IDs deliberately alias their immutable sources; custom rows retain existing precedence. Reject unexplained duplicate/cross-type ownership. |
| Identity and relationship | Resolve every student, guardian, staff and student/guardian edge from the appropriate captured publication context. Whitelist context fields. No PINs, emails, tokens or current pickup authority are inferred from an older snapshot. Version the semantic rules. Existing v1 copies can be read using their v1 rules and retained-source verification, but may not pass eviction automatically. For eviction, either prove complete closure against retained sources and publish a compatible verification supplement, or create a new complete publication before removal. Before removing sources, upgrade every affected historical read path to use that independently verifiable context/ownership index. Selecting an older snapshot must still return its captured values, not silently substitute the current publication. Unknown required columns/semantics fail closed. Optional historical context fields must not be interpreted as current authority.

Across publications, repeated immutable event/correction IDs must have identical hashes and contents; repeated identity context may legitimately differ and is selected by publication, not by last-write-wins. Visit/review snapshots may advance only through a verified transition. Validate a complete closure even when a request returns just one page; use previously verified immutable relation indexes plus verification of the requested objects, with their own pinned hashes. A page check must not claim to have freshly read every object in the archive.

## Late corrections, addenda and cross-month lookup

Use the **original arrival month** as the stable archive home. An effective correction from January to March updates the D1 effective interval/date index, while its addendum stays bound to January's base. This preserves the codec's same-month/timezone reference boundary and avoids searching only the user-supplied/effective month for a historical record. Keep the capture timezone immutable; current reporting timezone changes affect query boundaries, not object identity.

For a correction to an archived visit:

1. Authorize the manager and resolve the permanent correction ID before validating whether this is a new operation. Verify the archived visit head/evidence and show original and current effective values.
2. In one D1 batch, assert expected head/version, center ownership, backup/eviction fences and interval availability; append the complete immutable correction and audit evidence to `history_changes`; reserve the correction ID; advance the effective visit head/version; and increment affected report epochs. A hold preserves evidence and blocks eviction, but does not erase or silently prevent a legitimate recorded correction.
3. Return only after that D1 commit. Queue delivery is not the acceptance record. Retries resolve the outbox until publication, then its immutable R2 locator; both return the same accepted correction. Failed R2 delivery leaves the outbox intact and the updated interval enforced.
4. A bounded publisher captures a deterministic outbox sequence range, includes its identity/review/audit closure, writes immutable encrypted addendum objects, reads them back and runs the full semantic verifier. A conditional D1 commit publishes the new head and converts outbox locators to verified R2 locations. Only then may redundant outbox detail be removed through the same guarded preservation mechanism.

Reopening an archived visit requires an operational live projection so the roster and subsequent departure work normally. Rehydrate only the current visit projection through a dedicated controlled path; do not reinsert old observations through `attendance_apply` or replay audits. Preserve its original times/version and historical provenance, enforce the one-open-visit rule against all intervals, and retain historical detail in R2. A new closing observation becomes an addendum dependency. Re-eviction must wait until closure, resolved reviews, current retention cutoff and holds permit it.

Records previously excluded from a completed month may become eligible after a review resolves or a hold releases. Publish an admission addendum with the previously unarchived visit/event and its complete provenance; do not overwrite the month's base or assume it contains the whole month. Corrections accepted after a copy completed but before eviction also need an addendum or a new full publication. The old copy alone is stale.

The current format limits a graph to 16 references per manifest, depth 16 and 32 archives. An unbounded previous-addendum chain will eventually fail. Introduce a versioned publication sequence before enabling operational addenda: each bounded addendum can reference its immutable monthly base directly, while an authenticated ordered publication catalog carries the sequence and prior-publication digest. Recovery pins and verifies the complete required publication set, checks sequence continuity, and detects missing/conflicting branches. Do not weaken v1 limits or pretend one latest leaf proves every prior change. Batch several changes per addendum, define bounded catalog pages, and test rollover beyond these limits. The current 4,096-backup-reference and 512 MiB combined-recovery limits also need explicit capacity handling before the installation approaches them.

## Unified historical reading and report consistency

Introduce one resolver for visit detail, student attendance history, observed-event history, audit review, archived retry receipt and report evidence. Query compact D1 heads/locators, then decrypt only the bounded required R2 parts. Prefer live authoritative outbox/current projection over an older base; deduplicate by logical record ID/version. A copy that has not become the authoritative published history must not create duplicate attendance.

Keep owner/manager historical browsing and existing attendance-role retry permissions separate. The kiosk may resolve its authorized accepted event but must not gain bulk historical browsing. Continue private `no-store` responses, bounded POST bodies for sensitive filters, no PII in URLs/logs, and no browser/offline archive persistence.

Preserve the current report contract: date membership uses the **current effective arrival**, while exports include original times and complete observation/correction evidence. A January visit corrected into March appears in March once, even if all of its large records reside under January. Unmatched observations retain their observed-date scope. Provide explicit unavailable errors rather than dropping missing historical rows from totals. The SQL `audit_timeline` view remains a live-source view; every product path that promises complete history must use the unified resolver and reconcile its logical total, not mistake the shortened physical/view count for lost or complete history.

Report pages must pin the database restoration generation, affected live-date epochs, historical publication generation and relevant head versions. Build a deterministic, bounded index page and counts in one D1 view; fetch/verify its immutable objects; recheck the version fence before returning the page. Later pages must carry the same fence. A correction crossing dates increments the old and new effective-date epochs, as well as any original evidence scope used by event queries. Publication and eviction must either preserve an explicitly identical logical view or invalidate continuations; simplest first release invalidates them. Keep final count/relationship reconciliation before emitting a CSV.

The current per-request 366-day report bound is compatible with two-year review through multiple requests. It is not evidence that a complete two-year export has been tested; either provide an explicitly bounded multi-range export workflow or document the supported range without truncation.

## Atomic removal protocol

R2 and D1 do not share a transaction. The application can enforce immutable keys, readback, complete durable references and fail-closed reads; it cannot make an external administrator's concurrent object deletion atomic with D1. Configure private object retention/access controls, retain an independently verified recovery copy, and exclude required objects from lifecycle cleanup. Never describe create-only upload conditions as an R2 deletion lock.

Use small complete dependency closures, normally a closed visit with all its observations, corrections, reviews and logical audits, or one resolved unmatched event. Never split a relational closure merely to fit a part boundary. Cap rows/bytes/statements per batch; oversized or unsupported closures remain live with a clear blocked reason.

1. **Select and fence.** Under a transaction, choose only age-eligible, closed, resolved, unheld records; acquire an exclusive per-scope eviction lease and snapshot the exact closure and versions. Recheck both the original complete-month cutoff and the current effective departure cutoff; a visit corrected into the recent operational window stays live. Triggers fence updates and new dependencies for that closure during verification. Test inserts as well as updates: a newly appended audit/review/correction can invalidate an old membership set. Use database execution time for lease expiry, as the current archive runner does.
2. **Re-enumerate and verify.** With the fence active, compare every current source record/hash and relationship against the authoritative base plus published addenda. Check the complete graph from fresh private R2 reads, not just a stale `verified_at` marker. Materialize/validate permanent IDs, interval heads, identity/reference indexes and audit equivalence. If a source changed since its copy, publish the missing evidence first and restart. Do not trust externally computed hashes after a fence expires.
3. **Prepare a bounded permit.** Record the exact job/batch/fence, source closure digest, target manifest set digest, expected row counts, source/head versions and verified-at time. Only the internal removal transaction can consume it. No endpoint accepts arbitrary SQL, table names or a caller-supplied deletion permit.
4. **Commit one D1 batch.** Recheck the live lease token/expiry, backup lock, current source/head versions, exact closure counts, no extra referencing rows, all permanent locators, and active student/visit holds **inside this transaction**. Insert a transaction-local authorization row that is removed before the batch commits. Narrow delete triggers permit only its enumerated rows under this exact permit; all unrelated deletes remain rejected. Insert/verify the durable replacement indexes, then delete in foreign-key-safe order, assert exact affected counts and no remaining unaccounted dependency, write an immutable eviction receipt/audit, switch residency and report epochs, and consume the permit. A constraint/trigger failure must roll back the entire batch.
5. **Resume or reconcile.** Queue redelivery after a lost response sees the committed receipt and does nothing. A crash before commit leaves sources intact. A lost/expired lease cannot authorize deletion. Unpublished uploaded objects are harmless orphans and can only be cleaned by a separate reference-aware process. Do not use client memory or a successful queue acknowledgement as the source of truth.

Within the commit, remove resolved `reviews` and `attendance_corrections` before their referenced observations/visit; remove only archived physical `audit_entries` and preserve their logical replacements; then remove observations and the closed visit. Actual order must be derived from current foreign keys, including rebuilt holds and later CRM tables. Check both explicit foreign keys and logical references (`attendance_events.visit_id`, audit entities, outbox, schedules/CRM links if added). Do not turn foreign keys off or rebuild the evidence tables to bypass their guards.

Hold races have a defined order: if hold creation commits first, the removal transaction sees it and aborts. If removal commits first, the hold attaches to the historical visit identity and protects all referenced objects immediately. A hold API must resolve either live or historical identity within its transaction and cannot fail merely because a pre-read live row was removed. Release does not automatically remove records; the next batch still performs all checks. Student-wide holds cover every month and new addendum.

Migration of deletion guards must preserve default denial. Use tests proving that a row from another job/center, a stale permit, direct API/D1 delete, a partial closure, extra dependent row or unverified object can never pass. Durable job rows are not themselves a reusable deletion capability. The transaction-local authorization row exists only inside a successful atomic batch and never remains enabled between requests.

## Recovery, key custody and retention

Add every authoritative registry/head/publication/outbox/hold/eviction-receipt table to the SQL backup snapshot and its lock. Pin the exact publication set visible to the snapshot, including every old receipt locator and unresolved outbox dependency. A backup must represent either before or after a committed eviction, never a half-moved closure. Pending unpublished changes remain recoverable from SQL even if their R2 upload is absent.

Extend independent recovery to verify the semantic graph and reconcile each permanent key, effective head/version, logical audit count and locator against restored SQL plus immutable objects. SQL-only counts and valid ciphertext do not prove that a visit points to the right receipt. Restore indexes from their authenticated source and compare to the SQL projection; inconsistencies block activation. Rotate report generation, cancel stale eviction/publisher leases, clear transaction-local permits, and preserve committed receipts/outbox/history. Reconcile current holds and revocations after the restore point before reopening.

Retain the recovery encryption key in customer-controlled custody separate from the runtime and original account. Record a nonsecret key identifier/version for future rotation; do not mutate existing object hashes when rotating. Either retain old keys for their objects or republish a complete verified replacement with updated references and backup compatibility. Losing a key breaks the permanent receipt guarantee as surely as deleting an object.

No history GC in this release. Future GC must start from every active publication, permanent retry locator, hold, outbox, recoverable backup manifest and pending restoration; retain the complete transitive object set. Two-year minimum retention is not permission to delete ancestors of newer addenda or objects required by an older retained backup. Same-account R2 redundancy alone does not provide account-loss recovery.

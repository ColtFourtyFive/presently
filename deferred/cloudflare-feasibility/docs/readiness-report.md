## Recovery evidence and limits

The previously saved empty live schema-4 native export was encrypted locally, decrypted in a separate CLI process and restored into isolated local D1. All 23 table fingerprints/counts matched and integrity/FK checks passed. It was not a Worker-driven R2 backup, maintenance-fenced live export or independent cloud-account restoration. Its freshness must be re-established before an update. See [dated live validation](live-validation.md).

The independent CLI validates SQL and supported pinned v1/v2 archive graphs before publishing recovery output. V2 graph recovery and retained publication metadata restoration now pass locally. Restored publication availability remains disabled until fresh supported proof and full catalog reconciliation produce a current-generation receipt. Restore into an isolated database, apply current migrations and run the access-reset procedure before reopening. Reset invalidates staff/PIN/kiosk credentials, integrations, import previews, unfinished jobs and all semantic verification/cleanup capabilities while preserving evidence and completed archive metadata/holds. It cannot revoke provider credentials or disable the old deployment. Reconcile those separately.

D1 and R2 share the same Cloudflare account. Recovery after loss of that account requires a complete encrypted copy outside it and independent key custody. A backup also does not replace immediately accessible outage information. See [combined recovery](combined-recovery.md), [outage procedure](outage-procedure.md) and [customer handover](account-setup-handover.md).
